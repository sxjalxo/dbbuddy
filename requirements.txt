# Runtime + development dependencies for the DB Buddy server and engine.
#
# This file is the source of truth for a deployment. `pyproject.toml` declares
# only the narrower set the installable `dbbuddy` CLI needs.
#
# Version policy: floors, not pins. Lower bounds encode "this is the first
# release with the API we call", so security patches are never blocked by this
# file.
#
# `requirements.lock` is the compiled, fully pinned resolution of these floors —
# use it for a deployment that needs byte-identical builds. Regenerate after
# changing anything here:
#
#     uv pip compile --universal --python-version 3.12 requirements.txt -o requirements.lock
#
# `--universal` resolves across platforms and emits environment markers, so a lock
# compiled on one OS is still correct on another; without it a Windows machine
# produces a lock Linux CI cannot install.
#
# CI deliberately installs from *this* file, not the lock: resolving fresh is what
# surfaces an upstream release that breaks us, and finding that out from a nightly
# build beats finding out from a deployment.

# =========================
# AI / LLM
# =========================
# AI Insights (web app + `dbbuddy insights` CLI) needs no extra package — it
# reuses this same `requests`-based provider chain. Gated by INSIGHTS_ENABLED;
# `--local` insights talk to a local Ollama ($OLLAMA_URL / $LOCAL_MODEL).
# No vendor SDK: every provider is reached over its OpenAI-compatible HTTP API
# via `requests` (see dbbuddy_core/ai_providers.py). Adding an SDK would tie the
# adapter registry to one vendor's release cycle for no capability gained.
# `openai` was previously declared and is deliberately absent — see
# docs/ARCHITECTURE.md.

# =========================
# Embeddings / semantic layer
# =========================

# Heavy at import time: every process that touches the engine (pytest, the
# dogfood loop, a CLI call) loads Chroma and the ONNX embedder before doing any
# work, which costs hundreds of MB of RSS per process. Run verification serially
# — parallel runs are what exhausts a developer machine, not the queries.
chromadb>=0.4.24
# Backs Chroma's ONNXMiniLM_L6_V2 embedding function, which the vector store
# instantiates by name and holds process-wide (dbbuddy_core/vector_store.py).
# Chroma pulls it in today; pinned here because the import is ours, not theirs.
onnxruntime>=1.17.0

# =========================
# Strongly recommended at runtime (graceful fallback in code)
# =========================

# Shared cache, and the shared window behind the login/registration throttle.
# Absent, the engine runs every query live, the query rate limiter fails open,
# and authentication throttling degrades to a stricter per-process window. The
# code tolerates its absence everywhere; a multi-worker deployment should still
# have it. See docs/SECURITY.md.
redis>=5.0.0

# Secure API-key storage via the OS keyring (Credential Manager / Keychain /
# Secret Service). Falls back to a mode-0600 local file if no backend exists.
